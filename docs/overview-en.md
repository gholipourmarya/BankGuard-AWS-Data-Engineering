# BankGuard technical overview

**Operational status after teardown on November 4, 2026:** Following successful tests, all 73 Terraform resources and three additional snapshot catalogs were removed; the state is empty. KMS key deletion is scheduled. CloudWatch logs outside the state and the shared GitHub OIDC provider are retained. [Teardown evidence](evidence/2026-11-04/terraform-destroy/summary.json). The [AWS verification](evidence/2026-11-04/aws-verification.json) and [two successful MWAA runs](evidence/2026-11-04/airflow-runs.json) describe the earlier test state; 378 local and Docker tests passed.

BankGuard validates synthetic banking customers, accounts and transactions before analytical use. Valid records are published separately from rejected records; each rejection retains its reasons and source line.

Customers support optional `email` and `tel` fields, checked for basic syntax when populated. Metrics and rework reports cover all three datasets; CloudWatch quality alarms use `JobName` and `Dataset` dimensions. See the [data model](data-model.md) for exact rules.

The pure Python validator and CSV parser are shared between local execution and AWS Glue. References are validated in dependency order: customers, then accounts, then transactions. Accepted strings are trimmed consistently. Amounts must fit DECIMAL(18,2) exactly; money is never silently rounded. Embedded control characters in IDs are rejected. Synthetic unknown-account IDs use a separate namespace that cannot collide with generated references. Duplicate IDs retain the lowest source line as the original.

Automatic ingestion uses immutable `raw/batches/<id>/` packages. An uploader writes the three CSVs before the final `ready.json` marker. Lambda checks Glue job history to suppress repeat marker delivery and submits a queued run for that package. Lambda uses shared account concurrency and creates a permanent conditional S3 claim under `submissions/` before starting a new run. Concurrent deliveries cannot submit the same package twice. Interrupted or ambiguous submissions retain the claim and fail visibly until operator review; failed or expired runs require an explicit operator restart. Legacy packages without claims remain protected only by their existing Glue history.

Glue writes each run to its own snapshot prefix and creates a dedicated catalog database. A single S3 object, `published/current.json`, selects a complete snapshot only after all writes, partition registrations and the Glue commit have completed. Failed preparation leaves the previously published snapshot intact. It writes identical accepted transactions as CSV and Parquet for the scan comparison. A run-specific receipt under `runs/<Glue-run-id>/metrics.json` lets Airflow verify its own run, including zero accepted transactions.

SQL uses the selected Athena database instead of a hard-coded project name. The comparison tool disables result reuse and rejects unequal or empty query results. Readers resolve the publication pointer once and use that immutable database across related queries. Old snapshots and their catalogs require explicit cleanup. Script and library artifacts use content-addressed release paths and are switched together in one Glue job update. A scheduled poller alerts on ERROR and EXPIRED independently of Glue state-change events.
